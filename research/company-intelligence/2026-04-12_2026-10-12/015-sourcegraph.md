## Provisional, falsifiable direction hypothesis

Conditional 2027–2031 possibility: tooling that supports stronger retrieval, isolation and review may improve secure downstream code reuse. Rival explanation: more orchestration and dependency surface shifts work to reviewers and maintainers. Falsifier: unchanged/worse independently accepted task results per full human-plus-tool cost. This is an analyst hypothesis, not a company commitment.

**Study constructs:** M1 (workflow changes), M2 (acceptance/review), M4 (external integration), M5 (reuse instead of new build), M6 (lifecycle cost). See [central mission](../../../docs/AI_ERA_CODING_REUSE_RESEARCH_MISSION.md).

## Practical experiment (proposed, NOT executed)

Compare existing-code retrieval strategies against independently reviewed correct reusable candidates.

Freeze tasks, licenses and hidden independent acceptance criteria in advance, keep failures/abstentions in denominator, and record versioned source, developer effort, reviewer/repair minutes, upstream integration and security observations. kWh and CO2e are **not measured**; never infer them from token counts.

**Stop rule:** reject implementation if safety or reproducibility fails, independently validated task acceptance worsens or full maintenance burden exceeds the benefit.

### Feature map and constrained strategy inference

- **Code discovery:** Code Search (pre-existing baseline), Deep Search vendor-described qualitative/quantitative navigation, Code Finder as an agent-facing code-discovery tool, and Search Jobs as an integration surface. A search answer or exact link is a *candidate*, not proof that a library is correct, secure, licensed or suitable for reuse.
- **Review and code modification:** Compare-page navigation and Agentic Batch Changes vendor-described workflows (plan, propose, react to CI, request human approval). A generated PR is not a safely merged and independently accepted patch.
- **Architecture and rights:** API/MCP tools, token scopes, context filters, tenant-specific eligibility and self-hosted release versions affect whether an experiment is feasible. Recheck current license, endpoint permissions, version, model/data handling and geographic entitlements before adoption; none are independently certified in this note.
- **Direction classes:** Dated vendor notices above are class **A, vendor-reported product state** (not independently verified functional outcomes). No binding Sourcegraph **B, 2027–2031 company roadmap commitment** was authenticated. The following **C, analyst-only conditional inference** is explicitly separate: repository-scale retrieval and human-controlled batch migrations *might* increase genuinely reused code and decrease regressions **if** the retrieval accuracy, review effort, rights and lifecycle costs prove favorable. Rival hypotheses are increased false matches, longer review queues, licensing debt and vendor lock-in.
- **Counter-evidence/negative results:** Product marketing and its own benchmark are correlated first-party claims. No verified neutral held-out performance replication, source-rights audit or contradictory industry-wide study was established in this bounded review. **Not finding one here is not evidence none exists.** No user adoption, defect-rate improvement, energy saving, CO2e reduction or strategic certainty is claimed.

### Practical reproducible experiment for our repositories (E0 hypothesis)

**Decision to test:** For comparable real maintenance tasks, does an explicit *search-and-verify-existing-code* step improve **independently accepted functional task completion and appropriate verified reuse per total lifecycle cost** versus a conventional coding/agent process?

1. Register tasks, security and licensing exclusions, repository revisions and a randomized/matched assignment **before** examining candidate tools. Include no-reuse/unsuitable-dependency cases; distinguish within-repository discovery from verified *external* reuse.
2. Baseline with version-pinned `rg`/native GitHub code search and manually reviewed dependency metadata. Optional treatment with Sourcegraph Code Finder/Search Jobs **only when access, terms and cost are approved**; never assume a paid service, credentials or an API account is available.
3. Blind functional acceptance: independently authored tests and human/security/license review; record candidate precision, missing candidates, failed/abandoned tasks, CI and patch rework, total search/developer/reviewer minutes, fees and 30/90-day maintenance. A search miss is **unknown**, not proof a solution does not exist.
4. Primary outcome and uncertainty should count **all eligible tasks**, not just tasks yielding a nice PR. Verify downstream use/import against real version/license hashes rather than stars, code similarity or press.
5. Stop for security/rights violations, excess maintenance or worse independent acceptance. Report null and negative findings. Without metered provider energy, **do not** infer electricity or emissions from token counts or vendors' claimed speedups.

**M1/M2/M4/M5/M6 links:** workflow, independently judged quality, reused components, software verification and full task/lifecycle cost. M3/M7 discovery/adoption hypotheses require separate cohorts, not vendor changelog articles. See [mission](../../../docs/AI_ERA_CODING_REUSE_RESEARCH_MISSION.md), [experimental design](../../../docs/REUSE_FIRST_EXPERIMENT.md), and [lesson gate](../../../docs/EVIDENCE_TO_LESSON_PROTOCOL.md).
