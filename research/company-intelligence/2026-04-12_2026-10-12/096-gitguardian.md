Other Claude MCP outputs and **Cursor, VS Code, Copilot CLI, Kiro** tool outputs may **still reach the model**; their hook may only notify the developer after exposure. **Junie CLI** has hook support; **Junie within JetBrains IDE is not supported in 1.55.0**. Test each exact agent/tool event; do not label an entire agent “safe” from one checkbox.
- [Jul 8 generic detector notice](https://docs.gitguardian.com/releases/saas/2026/07/08/changelog) reports an **internal** 25–40% false-positive-classification figure on generic detections and Business/AI entitlement. There is no stated independently reproduced confusion matrix/eligible denominator for repository use. Vendor [Aug 27 incident attribution beta](https://docs.gitguardian.com/releases/saas/2026/08/27/changelog) sets an “Unrelated” outcome risk score to zero; if classification is wrong, a genuine event could be deprioritized. Keep human triage override and report both false-positive and false-negative cases.

**4. Non-code surfaces, supply chains and permissions.** [Aug 10 endpoint decoy AWS keys](https://docs.gitguardian.com/releases/saas/2026/08/10/changelog) need endpoint/honeytoken entitlement; [Aug 25 S3 scanning](https://docs.gitguardian.com/releases/saas/2026/08/25/changelog) uses user-provisioned read-only OIDC IAM role and handles archives, but launched as **on-demand historic scans**, not recurring scans; [Sep 4 NHI classification](https://docs.gitguardian.com/releases/saas/2026/09/04/changelog) needs ggscout >=0.32; [Sep 25 self-hosted 2026.9.0](https://docs.gitguardian.com/releases/self-hosted/2026-09-changelog) removes automatic personal-token renewal for Jira/Confluence Data Center: without renewed long-lived credentials, integrations break on expiry. [Sep 28 Coverage Hub](https://docs.gitguardian.com/releases/saas/2026/09/28/changelog) exposes integration/scan/owner statuses; [Sep 30 Wiz integration](https://docs.gitguardian.com/releases/saas/2026/09/30/changelog) synchronizes current VCS incidents once daily to an external security system with access rights and information-flow constraints. Neither metadata coverage percentages nor zero Wiz findings prove repository code safe.

[Oct 9 Harbor beta](https://docs.gitguardian.com/releases/saas/2026/10/09/changelog) is a **secret detector** applied to images and related artifacts; it does **not** establish malware screening, package-name integrity, SBOM completeness, vulnerability status, authorship provenance or license compliance. A secure reuse gate still needs independently inspected dependency identity, compatible license, signature/provenance where provided, vulnerable-dependency and maintenance checks, and functional task acceptance. A “secret-free” dependency can still be malicious or legally unusable.

**5. GitHub Apps and non-human identities:** [GitGuardian's Sept 22 security study by Gaetan Ferry](https://blog.gitguardian.com/github-app-private-keys-leaked/) says its researchers selected **4,802** contextualized private-key candidates from **more than 500,000 RSA-key detections**, and reported **474 keys** authenticating as **440 distinct GitHub Apps**; 44 Apps reportedly had org-admin permissions. These are **vendor self-reported outcomes from a selected frame**, *not* 474/4,802 prevalence of leaks among GitHub Apps, not a representative sample, not an independently validated exploit count, and not proof GitGuardian itself prevented leaks. Underlying case leaks occurred in earlier years; the publication is Sept 2026. This is one eligible, nonduplicate public-security research **news lead** for [corpus #56](https://github.com/MSKazemi/github-trending-1000-study/issues/56); a provisional single-reviewer JSON item should explicitly retain this selection bias if admitted.

## D. Data, security, privacy, package identity and rights safeguards

The relevant trust boundaries for an agent-assisted OSS research repository include: (a) a human's source tree and local shell output; (b) agent prompts and file-read or MCP/tool outputs; (c) local agent transcripts and caches; (d) secret-scanning API/cloud service; (e) Git commit/pre-commit/pre-push; (f) GitHub Actions runners; (g) any connected GitHub App, PAT, cloud role or third-party security integration. A successful block at **one** boundary does not guarantee all the others. For the maintainer's repo, do not send production tokens or unapproved private content to a scanning API merely to test it. Evaluate data-processing agreement, telemetry retention, agent subscription metadata, per-tenant scopes, API access, network egress and false-positive handling before deployment.

Before adopting code or a package: pin the **exact name, version, registry/project identity and cryptographic digest**; check the OSS license at the selected tag and each dependency's license; verify native artifact signatures/attestation if supplied and actually validated; review release maintenance and known advisories; scan only authorized material, with least-privilege credentials and fail-closed behavior if the scanner becomes unavailable. Do **not** execute remote install pipelines such as unreviewed `curl ... | sh` as a convenience, or turn sample GitHub App keys into test data. Different ggshield distribution paths and optional signature bypasses merit explicit review. A repository's availability, stars or license badge is not evidence of safe reuse.

**Important scope:** a GitGuardian detector can help with **secret exposure**, but is not a substitute for SLSA/Sigstore provenance checks, package-install trust decisions, a license and vulnerability scanner, code review, access-control enforcement or independent external functional validation.

## H. One falsifiable, small maintainer-repository pilot (not implemented)

**Repository and outcome:** [MSKazemi/github-trending-1000-study](https://github.com/MSKazemi/github-trending-1000-study); functional unit **one independently accepted, benign agent-assisted repository maintenance task** completed **without causing a synthetic secret exposure across declared surfaces**, maintaining functional correctness and reviewer acceptability. This is a prospective *security integration feasibility experiment*; **n=12 proposed tasks is not a powered causal trial**.

**Predeclare and freeze:** a documented 12-task, version-pinned set and acceptance SHA before condition allocation: four synthetic credential-shaped positive cases with *guaranteed nonworking values*, four benign lookalike negative controls, four tool-output/file-read/commit-boundary cases. Include scanner errors, disabled/unapproved hook, `core.hooksPath` override, local session persistence and unsupported agent modes as prespecified negative tests. An **independent reviewer**, not the coding agent generating the patch, owns the hidden acceptance and threat labels. If a synthetic pattern is **not** an actual supported detector signature, label it *ineligible/unknown detection coverage* beforehand rather than invent a false-negative result.

**Comparator and treatment:** run the **same** frozen maintenance tasks on disposable isolated forks/worktrees: **A = existing repository documented code review and CI workflow**, **B = identical workflow plus a pinned and permission-reviewed GitGuardian `ggshield` version (v1.55.0 candidate), with pre-commit/CI check and an actually approved *supported* AI hook**. Match agent version, OS, environment, account permissions, baseline code, execution budget and CI conditions. Randomize task order/paired condition when feasible; preserve every assigned task including abstentions, incomplete work, broken scans and timeouts. Do not install software, contact cloud scanning endpoints or transmit even dummy artifacts without separately approved network/terms/retention review. If real hooks or permission cannot be authorized, run **only an offline dry-run feasibility check** and explicitly mark actual treatment effect **unmeasured**.

**Primary outcome:** number of 12 assigned tasks passing **both** independent functional acceptance and exposure guardrails, reported per arm with complete denominator and uncertainty/feasibility caveat; report misses/fail-open states by exposure stage. **Secondary outcomes:** falsely blocked benign tasks, number of unscanned unsupported tool events, unintentionally persisted synthetic outputs, human setup/triage/review/rework minutes, CI retries and runtime, optional vendor cost/quota, and a prospective 30-day change-maintenance check. Distinguish detection, *prevention before model access*, and local persistence—three different outcomes. Use no real credentials or users and do not claim a measured 30-day follow-up that has not happened.

**Stop/reverse rule:** halt or reject treatment on **any real private-data network/transcript disclosure**, an unapproved privilege/telemetry expansion, a bypass of a declared high-severity supported test with no safe mitigation, failure of independent functional acceptance, lack of required license/data-processing authorization, or materially increased total reviewer/CI burden without a demonstrable safety improvement. A null/worse result is publishable and means **do not scale**. No kWh, CO2e, token-to-energy conversion, new user cohort or quantified security improvement is claimed in this report.

**Low-regret implementation lesson now:** for the study repo and other maintainer projects, keep GitHub App keys and service tokens out of agent transcripts and committed fixtures; configure least-privilege short-lived automation credentials and verify approvals, revocation and no-echo handling. A vendor hook or service should pass the independently frozen end-to-end test before depending on it. Prefer adapting a vetted MIT tool or existing CI control over writing a duplicate scanner, **only after task/license/privacy acceptance**.
