## 4. Public strategy vs hypothetical outlook (2027–2031)

**Company-attributed public direction:** Lovable combines reusable instruction bundles, delegated building, draft isolation and more productized security; incidents show safeguards require independent and ongoing verification. No guaranteed 2027 roadmap verified.

**Confirmed binding future releases:** none established by this pass. Announced intentions do not amount to delivery schedules.

**Analyst hypothesis, not a company promise (E0):** Reusable checked project scaffolds/drafts may improve onboarding and prevent accidental live breakage; however, cloud permissions and generated dependency vulnerabilities can create hidden cost and risk.

**Confounding / alternative mechanism:** Better vendor UX may increase prototypes but not long-lived maintainable and externally reusable software; closed hosting confounds reuse. A disconfirming result is a randomized or matched test showing no added independently accepted task value, or higher lifetime cost and security incidents despite more generated work.

## 5. Connection to study constructs M1–M7

- **M1 workflow chronology:** preserve date and exact feature availability; do not equate tool release with verified developer adoption.
- **M2 accepted code quality/effort:** independently judge fixed tasks and failures/abstentions, rather than patch counts or anecdotes.
- **M3 visibility:** stars and promotion are *attention*, never sufficient for actual reuse.
- **M4 externally reproducible adoption:** require clean external first-use and downstream integration with an eligible denominator.
- **M5 reuse versus new build:** compare package discovery + license/security/version checks against bounded new build.
- **M6 lifecycle sustainability:** include planning, reviews, inference, CI, runtime, upgrades and upstream maintenance; **no token-to-kWh or carbon conversion**.
- **M7 ethical adoption:** only organic, task-verified contributor/user onboarding evidence—not purchased stars or low-value PR activity.

## 6. One practical falsifiable repository experiment

**Repository for initial pilot:** `MSKazemi/github-trending-1000-study`, with only its existing offline code/docs/fixture surfaces. **Proposed—not executed:**

Prototype a tiny docs+static interface for the repo twice: existing verified template with manual build versus a controlled prompt-built draft. Exclude real credentials. Freeze requirements and deploy/portability acceptance; independently check exported source/build, XSS/dependencies, accessibility, provenance, human repair and support cost.

**Acceptance design:** before assignment, a person other than the implementing agent must freeze the task description, user success conditions and hidden tests. Use fixed versions, identical safe fixtures and matched task difficulty; record the sampling frame and every refusal, timeout, unsuccessful run or abstention. **Primary endpoint:** fraction of independently accepted tasks with an explicit denominator and uncertainty. **Secondary:** downstream clean-install success, matching legal package identity/license, reviewer-repair minutes, money actually billed or clearly modeled and version drift at 30/90 days. Report kWh/CO2e only if instrumented with a documented system boundary and sensitivity analysis.

**Stop / rollback rule:** Do not publish generated app without independent threat review, precise ownership/hosting permissions and successful external clean build; disclosure-based risks supersede speed claims.

**Expected null/negative scenario:** no difference in accepted-task results, higher maintainer or review costs, poorer security, portability or upstream rights, or inability to obtain externally valid task ratings. Do not turn a null result into a fabricated positive lesson.

**Researcher's conditional interpretation (E0 hypothesis).** The hypothesis has four premises:

- Lovable keeps concentrating new apps on one vendor-chosen stack (009).
- Lovable patches hosted apps centrally (050).
- Lovable charges for repair loops (034).
- Lovable makes export and two-way sync easier (036, 043).

If those hold, then maintainers who export will take on the upstream patch and migration work that hosted users get for free. The real lifetime cost of a generated app will then depend mainly on whether it stays on Lovable hosting, not on how it was generated (M5/M7).

- **Falsifiers:**
  - exported apps receive the same automatic dependency upgrades;
  - measured repair minutes for exported and hosted apps do not differ over two or more upstream advisories;
  - the stack default changes without a migration burden.
- **Rival explanation:** the concentration reflects a sound engineering choice (SSR for discoverability) and lowers total risk compared with a spread of unmanaged stacks.

### Refinement of the §6 experiment (proposed, not performed)

The earlier §6 design stays as written. The new evidence suggests one bounded addition: **an export-portability arm.**

- **Task:** take one Lovable-generated app built in the existing §6 arm, export it (zip or GitHub sync), and build it on a clean machine with pinned Node.
- **Unit of accepted work:** an independently written smoke test passes, `npm audit` shows no critical advisory against the version pinned at export, and the app runs without Lovable-hosted services.
- **Comparator:** the same app kept on Lovable hosting.
- **Guardrails:**
  - no real credentials or personal data;
  - no network capture of other projects;
  - project visibility kept private (row 004);
  - no paid plan or credit spend without the maintainer's prior approval;
  - opt out of model training before any content is entered (row 029).
- **Measurement:** human minutes to get a clean external build, and to apply one upstream security update by hand.
- **Stop rule:** stop if the export needs paid features, or if the exported build cannot pass the smoke test within two hours of human work.

Creating a Lovable account is a human decision and is not done by this upgrade.
