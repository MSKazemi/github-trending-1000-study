## Provisional, falsifiable direction hypothesis

Conditional 2027–2031 possibility: tooling that supports stronger retrieval, isolation and review may improve secure downstream code reuse. Rival explanation: more orchestration and dependency surface shifts work to reviewers and maintainers. Falsifier: unchanged/worse independently accepted task results per full human-plus-tool cost. This is an analyst hypothesis, not a company commitment.

**Study constructs:** M1 (workflow changes), M2 (acceptance/review), M4 (external integration), M5 (reuse instead of new build), M6 (lifecycle cost). See [central mission](../../../docs/AI_ERA_CODING_REUSE_RESEARCH_MISSION.md).

## Practical experiment (proposed, NOT executed)

Freeze tasks, licenses and hidden independent acceptance criteria in advance, keep failures/abstentions in denominator, and record versioned source, developer effort, reviewer/repair minutes, upstream integration and security observations. kWh and CO2e are **not measured**; never infer them from token counts.

**Stop rule:** reject implementation if safety or reproducibility fails, independently validated task acceptance worsens or full maintenance burden exceeds the benefit.

### M1–M7 notes for new events

- **M1 agent workflow:** in six months GitHub moved from an assistant to a platform of agents with an SDK, desktop app, sandboxes, Actions-hosted agentic workflows and third-party agents. These are chronology markers, not adoption evidence.
- **M2 discoverability:** the stargazer restriction and the new star-history endpoint change how star growth can be measured (aggregate only, non-UTC buckets). Fake-star and malware-clone reports question raw stars and search results as quality signals. `author:` search now mixes human and agent PRs.
- **M3 verified reuse:** the Copilot SDK (MIT), the Eclipse plugin (MIT), Agent Plugins 1.0 and Agent apps are reuse surfaces. The Models, Spark and Classroom retirements show how fast vendor-hosted components can be withdrawn. No independent reuse measure exists.
- **M4 accepted task quality:** ReviewBench and the stacked-PR metrics are vendor-defined. The Wiz/Snowflake case shows scanning and AI review can both miss a critical workflow flaw (single case).
- **M5 review/maintenance:** PR limits, stacks, code-review effort levels and AI approval are all aimed at review load. The Node 20 removal and model churn (44 model notices) add maintenance work.
- **M6 rights/security/provenance:** one CVE, one breach, one prompt-injection disclosure, supply-chain defaults and push attribution. Attribution changes put "@copilot" into release notes and searches, which matters for repositories whose policy forbids AI contributor attribution.
- **M7 lifecycle cost:** AI credits are metered by tokens. Code review consumes Actions minutes. The Rust port reports $120,000 in tokens. None of this is converted to kWh or CO2e here.

### Bearing on the experiment (still proposed, not performed)

The earlier worktree-versus-sequential sketch stands. Two maintainer-relevant facts change its measurement. First, star-based outcomes can no longer use per-stargazer lists for non-collaborators, so any downstream-discovery outcome must use `GET /repos/{owner}/{repo}/stargazers/history` (weekly, non-UTC boundaries) or `…/stargazers/count` and record the API version used (`2026-03-10` in our check). Second, GitHub's search and release notes now attribute agent-opened PRs to the requesting human ("@user with @copilot"). A repository that forbids AI contributor attribution should review its release-note generation and must not use `author:` counts as human-only effort. A vendor-neutral comparator now exists for the review arm: the same frozen change submitted as one PR versus as a stacked series, with reviewer minutes and defects found as outcomes, failures kept in the denominator, no paid API spend without approval, and stopping if either arm needs permissions the task does not require.
