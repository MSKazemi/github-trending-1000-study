## 8. Practical, falsifiable pilot for the maintainer's own repository

**Repository:** [GitHub Trending 1000 Study](https://github.com/MSKazemi/github-trending-1000-study) (existing offline CLI and synthetic fixture; do not scrape live Trending).

**Practice to test:** Compare creating a bespoke task orchestration wrapper against reusing a fixed, versioned task spec and existing project Python commands.

**Treatment/comparator:** A: write new workflow glue to invoke parse+summary; B: keep current CLI and use versioned declarative task instructions; same frozen synthetic fixture.

**Freeze before treatment:** same repository SHA, dependency/model versions, synthetic inputs, objective expected outputs, task/time cap and evaluator; record failures and no-solution tasks. A second person creates or freezes acceptance tests before any agent-generated change.

**Primary outcome and verifiable reuse:** Independent evaluator accepts the same output checksum/schema and correct failure handling; log human minutes, build/API costs and 30-day compatibility.

**Costs / constraints:** record active human time, reviewer minutes, task-level billed/model tokens where known, CI runtime, 30-day defects, code provenance, package-license/security checks and any upstream support work. Tokens/LOC/stars are **not kWh or CO2e**. Prospective experiment **not run**; sample size/power and human consent not secured.

**Stop/reversal:** Reject B if preview/vendor dependencies or scope changes increase total cost or introduce uncontrolled data exposure.

**Transferable maintainer lesson:** prefer a reusable, versioned interface with an independently testable first-use task over a flashy new repository; test whether verified outside use improves without shifting hidden maintenance/security costs.

### Documentary recheck — 2026-10-13 (analyst pass, not independent reviewer)

- **Strong direct example of not reinventing infrastructure:** [Mistral Workflows April 27 technical article](https://mistral.ai/news/workflows/) explicitly reports building on **Temporal's existing durable-execution engine**, adding AI-oriented streaming/payloads, multi-tenancy and observability. Its Python SDK and workspaces are described, but reliability, cost and portability outcomes are vendor reports rather than our measurements.
- **Important data-plane boundary:** The same article describes a **Mistral-hosted control plane** and **customer-environment Kubernetes workers**. Reuse might transfer operational burden; test auth, credentials, data residency and incident recovery before calling it a net improvement.
- [Mistral Large 4 October 6 announcement](https://mistral.ai/news/mistral-large-4/) states a **public-preview API**, **52B active parameters** and a plan to publish weights **later in October**. **Do not count those weights as shipped by October 12 or label the preview generally available**. Its own benchmark numbers remain first-party claims.
- [July 9 Studio prompts/skills versioning](https://mistral.ai/news/manage-prompts-and-skills-in-studio/) reports a system of record. This suggests *testing reusing versioned instructions and connectors*, not claiming it automatically reduces maintenance.

**Revised pilot contrast:** Compare the existing Python CLI + test harness against any new workflow layer only when the task actually requires durable retry/resume/approval. If it does, evaluate an existing Temporal integration before proposing custom orchestration; record incremental deployment and review cost.
