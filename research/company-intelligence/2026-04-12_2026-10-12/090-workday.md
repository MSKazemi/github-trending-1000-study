## 2. Verified company/product identity and baseline

Workday sells cloud HCM, financials, planning (Adaptive Planning) and, from 2026, describes itself as "the enterprise AI platform for HR, finance, and IT". Its AI products in window were branded as **Sana** (agentic assistant, from the Sana acquisition) and Workday **agents**. The older **Illuminate** branding appears only in pre-window releases (for example 2025-09-16). Developer surfaces are **Workday Build/Extend** (custom apps and agents), **Agent-Ready Tools** over MCP, the **Agent System of Record (ASOR)** with a [public specification repo](https://github.com/Workday/asor), **Workday Data Cloud** (Data Lake, Data Connect, Live Data Query) and Pipedream connectors. The core platform is proprietary. The open-source footprint consists of Apache-2.0 sample, client and tool repositories in the [Workday GitHub org](https://github.com/Workday) and, until its archival, the Flowise agent builder (Apache-2.0 outside an enterprise directory that carries a commercial licence per `LICENSE.md`).

Pre-window baseline, for context only: Flowise acquisition (2025-08-14); Sana closing (2025-11-04); Pipedream agreement (2025-11-19) and closing (reported in FY26 Q4 release, 2026-02-24, which also claims "1.7 billion AI actions" in FY26); CEO change (2026-02-09); Mobley v. Workday collective certification (May 2025) and a March 2026 order discussed in [HRExaminer, 2026-03-20](https://www.hrexaminer.com/p/what-the-court-actually-did-in-mobley); 2025 third-party-platform data incidents (search snippets only, not verified). **Post-window, excluded:** nine 2026-10-13 Rising releases. These include GA of Developer Agent, Agent-Ready Tools, Custom Agents, Agent Harness and Data Cloud, an Anthropic partnership, and an agreement to acquire C1.ai.

## 8. One practical, falsifiable change for the maintainer's own repositories

**Repository/component:** [github-trending-1000-study](https://github.com/MSKazemi/github-trending-1000-study) Python package and its declared dependencies (`pyproject.toml`), offline. The disabled Trending `capture` command stays disabled. No network collection is involved beyond public registry/advisory metadata, and only with approval.

**Candidate practice (not yet validated):** Add a **dependency-lifecycle gate**: before merging any PR that adds or upgrades a dependency, check the upstream repository's archived flag, latest release age and advisories with empty `patched_versions`. Reuse first: compare existing tools (GitHub Dependabot alerts, `pip-audit`, OSV data) with a short script that only reads the GitHub `archived` flag. Do not build a new scanner. The Flowise case motivates this: archival plus six post-EOL advisories with no patch.

**Treatment/control and frozen comparable task:** Freeze a set of 10 synthetic "add dependency X" PR tasks. Some (unknown to the reviewer in advance) name archived or advisory-laden packages, such as a pinned `flowise`-like case from public metadata, and others name maintained packages. The task list and expected verdicts are written by a person other than the operator and hidden from any agent. Arm A: the current review with unit tests and `pip-audit` if already used. Arm B: Arm A plus the lifecycle gate. Accepted-task unit: a PR verdict (accept/reject with reason) that matches the frozen expected verdict.

**Success and guardrails:** Primary: correct verdicts / all 10 tasks, with refused or timed-out tasks counted as failures. Guardrails: no new runtime dependency in the package; no credentials beyond read-only public API access; full unit suite green; no network access in tests (fixtures only). Measured human work: setup minutes and per-PR review minutes. No paid API spend without approval, and no energy or CO2e estimate unless metered.

**Stop/reversal rule:** Keep Arm A if Arm B does not catch at least one more problematic dependency than Arm A on the frozen set, adds more than 3 review minutes per PR on average, or produces more than 2 false alarms out of 10. **No trial executed; no effect estimated.**
