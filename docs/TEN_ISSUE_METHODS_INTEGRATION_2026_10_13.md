**Repository:** https://github.com/MSKazemi/github-trending-1000-study  
**Scientific focus:** AI-era source-code reuse, independent functional usefulness, attention versus adoption, upstream/downstream maintenance burden, and honest life-cycle environmental trade-offs for the 2027 study.  
**Evidence status:** reproducible *research infrastructure* improved, not completed empirical research. No new participants, official source crawl, externally accepted task, independently authenticated human rating, metered kWh or measured avoided emissions were collected in this session. Synthetic fixtures are deliberately not empirical observations.  
**Related PR review:** [2026-10-13 PR integration record](PR_REVIEW_2026_10_13.md).

## 1. Research questions and scope of inference

- **RQ-A — Discovery versus functional reuse:** On prospectively frozen, independently specified tasks, do reuse-first lexical, embedding or hybrid retrieval workflows improve *independently accepted functional integrations* relative to a registered comparator under fixed search/inspection budgets? Ranking precision alone is secondary and cannot establish adoption.
- **RQ-B — First-use usefulness:** Do archetype-appropriate documentation and interface improvements change actual first-time user task success, elapsed human effort, and opt-in repeat use when tasks and acceptance criteria were frozen independently? A star or download is not a completed task.
- **RQ-C — Representation and selection:** How much of an independently established component/dependency frame is missed by a Trending-only discovery channel, including older, small or low-attention repositories? Do not estimate missed global reuse before establishing source-frame coverage and inclusion probabilities.
- **RQ-D — Reliability and transfer of burden:** Under the same accepted functionality, how do license/security suitability, upstream reviewer time, support costs, maintenance over 30/90/180 days, and failed attempts differ between build, reuse and assisted variants? An agent-generated patch count is not an outcome.
- **RQ-E — Sustainability:** Under a calibrated, declared boundary and equal independently accepted task output, when is the *signed* energy (and, where justified, CO2e) change for reuse versus build positive, negative or unknowable as usage, maintenance, model inference, embodied hardware and rebound vary?

These are *questions and prespecified directions*, not observed findings or registered hypotheses with statistical approval.

## 3. One coherent study architecture, not ten incompatible studies

1. **Evidence discovery:** #7 builds a reproducible, source-class-separated and dual-screened bibliography. Research questions and inclusion/exclusion rules are frozen *before* screening. Cross-DOI title matches are review leads, not confirmed duplicates.
2. **Sampling and task freeze:** #15 defines a separate quiet-OSS sampling frame as well as a Trending frame. Freeze source timestamps, stable GitHub numeric repository IDs, exact package identity, strata, task specification/acceptance SHA-256 and an outcome-blind seed. Include older repos when eligible; age alone is not an exclusion.
3. **Human measures:** #5 develops blinded archetype-specific documentation quality measures; #8 defines accepted user-task functionality, with independent raters rather than agent self-scoring. Do not rely on synthetic reviewer identifiers as proof of people.
4. **Reuse discovery and safety:** #19 evaluates lexical, embedding and hybrid retrieval using the same candidate frame and fixed budget. #22 screens exact package/version/license/advisories/provenance before any sandboxed acceptance test. A model similarity score never bypasses license/security constraints.
5. **Longitudinal consequences:** #12 measures verified downstream integrations and opt-in repeat use with explicit missing/attrition. #24 adds actual upstream reviewer, support and downstream human-time costs, including failed attempts and rejected submissions.
6. **Sustainable computation:** #18 maps the functional-unit energy measurement boundary; #23 computes signed build-versus-reuse break-even scenarios and reports missing provider/embodied/rebound terms. Physical energy, human labor, CO2e, license harm and community burden are *different outcomes*, not interchangeable proxy units.

### Shared identity and unit contract

For every real record, plan to bind:
- a frozen task ID, task/source timestamp, versioned requirements and independently authored acceptance SHA;
- stable GitHub repository numeric ID (plus observed mutable owner/name), package URL or purl and exact dependency digest/version;
- project archetype, language/ecosystem, inclusion stratum, source selection probability **when justified**, and counterfactual comparator;
- arm/model/tool/version, retrieval index corpus, search time/cost, license/security and functional gates, candidate availability before baseline;
- assigned task status (pass/fail/abandoned/refused/pending), missing/withdrawn/N/A flags, consenting participant pseudonym and independent rater evidence under approved access;
- metering configuration/calibration, physical kWh units, grid region/time, provider-model and embodied uncertainty, 30/90/180-day downstream and upstream maintenance.

Do not combine heterogeneous denominators (repositories, candidate packages, independent tasks, independent *users*, search attempts and code releases) or treat repeated tasks by one user as independent users.

## 4. Proposed registered analysis plan — not yet executed

**Design:** prospective, matched tasks selected independently of solution availability. Where permitted/ethical, compare human and agent usual versus reuse-first via the *existing* repository trial assignment code, cluster related task families, record preassignment exclusions, and keep **all assigned tasks** in the intention-to-treat denominator. For software tasks derived from public issues, explicitly distinguish practical maintenance using visible fix hints from a supposedly held-out problem-solving benchmark; pretrained-answer contamination cannot be assumed absent.

**Primary endpoint candidate:** verified, security/license-acceptable, independently accepted task completion on frozen test suites by the preregistered time/budget horizon. Define failure, abandonment, refusal and incomplete observation in advance. If a task cannot receive independent acceptance, classify it unknown/unassessable rather than failure or success.

**Main contrasts:** assigned-task acceptance difference for reuse-first versus usual workflow; conditional resource/effort cost of *accepted* tasks as a secondary estimand with explicit selection caveat; independently verified downstream integration within the predeclared eligible panel; retrieval P@5 bounds, not global recall. Prespecify subgroup strata and comparisons; correct exploratory multiple testing or clearly label it exploratory.

**Uncertainty:** use task-family/participant clustered methods or paired assignment/permutation where appropriate. Report absolute effects, compatible 95% intervals only where real data and design justify them, sample size, denominator, unanswered tasks and missingness sensitivity. Logical worst/best-case missing-outcome bounds are useful to show uncertainty **but are not confidence intervals**. Archetype-specific κ is descriptive and prevalence-sensitive; very small strata yield null/undefined κ.

**Break-even:** for an explicitly additive scenario, signed energy difference at n accepted uses is

Delta E(n) = (E_build_fixed - E_reuse_fixed) + n (E_build_runtime - E_reuse_runtime).

This equation is a *model specification*, not a measured reduction. Include search failures, unsuccessful installation/review, update and cache/index maintenance, upstream labor separately, hardware/CI, inference uncertainty, service levels and workload rebound. Unknown included kWh terms prohibit a total point estimate. No universal grams CO2e per token and no green claim from fewer lines of code.

**Independent gates, in order:** lawful data/source access -> preregistered study + privacy/consent -> complete eligible task/candidate frame -> independent test and source review -> instrument calibration -> pilot variance/missingness -> approved confirmatory sample/power and randomization -> outcome collection -> blinded adjudication -> analysis and replication -> reviewable context-bounded maintainer lessons. Passing GitHub CI is only an engineering gate, not one of the independent scientific signoffs.

## 5. Threats to validity and explicit stop rules

| Threat | Required control | Consequence if unmet |
|---|---|---|
| Selection after knowing which solution works | Frozen independent task and source frames; prospective inclusion log | Only exploratory claim, no efficacy inference |
| Public source code/solution leakage into task spec/model | Distinguish maintenance from held-out solving; reviewer contamination log | Do not claim independent solution discovery |
| Stars/Trending/downloads used as reuse evidence | Require versioned downstream import/integration and user task acceptance | Report attention/distribution only |
| Unknown candidates or withdrawn participants hidden | Keep unknown, N/A, withdrawal, attempted/assigned denominators and bounds | No population-representative prevalence |
| Favorable self-reported vendor claims | Link original official source, date and claim type; independent verification before extraction | Source lead only; no deployment/performance proof |
| Silent security/licensing omission | Version-specific registry source, license obligations, advisories, sandbox and explicit reject/defer | Block automatic reuse/installation |
| Missing inference/embodied/rebound and maintainer externality | Record explicit unknown and partial boundary; separate labor from electricity | No total net energy/carbon conclusion |
| Volunteer or single-ecosystem convenience cohort | Project-type, language, old/quiet repositories; coverage assessment, consent and clustered analysis | Narrow exploratory applicability only |
| Concurrent AI agents duplicate instruments | Check issue, changed-file, schema and PR inventory before writing; merge unique tests/leads into one canonical module | Defer new module and reconcile |
| Consent/privacy or platform permission failure | No unsolicited PR flooding, private-person profiling or unauthorized scraping | Stop field data collection immediately |

## 6. Referenced research standards (for method design, not evidence of results)

- [PRISMA 2020 reporting guideline (BMJ)](https://www.bmj.com/content/372/bmj.n71): systematic review reporting and transparent inclusion decisions.
- [Runeson & Höst (2009), case study guidelines in empirical software engineering](https://doi.org/10.1007/s10664-008-9102-8): cases, source traces, protocols and validity threats.
- [Cohen (1960), agreement for nominal scales](https://doi.org/10.1177/001316446002000104) and [Byrt et al. (1993), prevalence and bias effects on kappa](https://doi.org/10.1016/0895-4356(93)90018-V).
- [Cochrane Handbook, Chapter 10](https://www.cochrane.org/authors/handbooks-and-manuals/handbook/current/chapter-10): caution interpreting incomplete or selectively missing outcome data.
- [ISO/IEC 21031:2024 Software Carbon Intensity](https://www.iso.org/standard/86612.html): declared functional units and carbon accounting boundary.
- [SPDX license-expression specification](https://spdx.github.io/spdx-spec/v3.0.1/annexes/spdx-license-expressions/), [OSV API](https://github.com/google/osv.dev/blob/master/docs/api/post-v1-query.md), and [Package URL (purl) specification](https://github.com/package-url/purl-spec): identity, license and advisory-retrieval standards.

Sources above support *methods and terminology* only. They do not independently verify a source/example from this repository or constitute ethical approval.

## 7. Practical lessons for the maintainer's own repositories — to test, not assume

1. **Reuse search before generation:** for one incoming, independently testable CLI/library issue, freeze a failing test; search existing code/dependencies at a bounded time and query budget; reject wrong-license/unsafe/out-of-date matches before integrating; document every abandoned candidate.
2. **Make first use reproducible:** provide one clean-environment installation command and runnable example; ask consenting outsiders to perform the task; measure independently accepted success, not README length, stars or GitHub SEO rank.
3. **One canonical implementation per capability:** require parallel agents to inspect the open-PR file inventory and tool contracts. Reconcile competing modules with shared tests and retained provenance rather than count duplicate PRs as progress.
4. **Include real human work:** record maintainers' review/rework and 30/90-day dependency upgrades as well as agent/API/CI time. No human-minute-to-kWh conversion without separate measurement.
5. **Publish negative/unknown outcomes:** if source access, consent, functional tests, package security, retrieval recall or model inference energy is unavailable, preserve unknown; publish conditional scenarios and clear stop rules rather than persuasive but false success statistics.
6. **Review trends carefully:** a new repo's attention may reflect agents or promotion; older low-star packages can be valuable reusable infrastructure. Validate reuse with actual independent integrations and an outcome-blind comparator.

**Bottom line:** Ten issue-linked methodological workstreams have materially improved, and their CI tests pass, but real datasets, independent reviewers, calibration and preregistration remain the high-priority scientific work. Issue completion should be decided by these **empirical acceptance criteria**, not by a green CI badge or PR merge.
