## Suggested merge order and gates

1. **Resolve direct-file collisions first:** pick one versioned company report and one evidence-registry schema; preserve unique evidence leads and negative tests in audit-friendly commits; retire superseded drafts only after reconciliation.
2. **Complete offline technical review:** check latest-head CI, version compatibility, parser/security regressions, tests for unknown/null/future data, no destructive writes, no untrusted code or unauthorized platform fetching.
3. **Separate technical integration from scientific acceptance:** method-changing PRs #170/#190 explicitly require human signoff; a merged instrument would remain provisional, not approval for field data collection. For reports, require independent publisher-date/link/claim verification and disclosed conflicts.
4. **Keep source and task denominators:** missing or inaccessible items are unknown, not zero; publication/release is not software adoption, Trending/stars are not external code reuse, and tokens are not energy or CO2e.
5. **Pilot reuse-first on a frozen task:** search compatible existing tools/PRs, verify license/version/security, integrate once, and evaluate independent accepted functionality, outsider repeat use, reviewer burden and bounded lifecycle costs. Preserve negative results.

## Practical 2027 lessons for the maintainer's other repositories

- **One capability, one canonical implementation:** parallel agents should check the PR/file inventory *before* writing a new module or company report. Duplicated research itself wastes review attention and compute.
- **Evidence-aware PR template:** task/issue; exact changed paths; reuse search; claimed versus measured outcomes; source URLs/dates; limitations; tests/CI; human gate; and supersession links.
- **Automate structural integrity, not scientific authority:** versioned schemas, UTC chronology, immutable source anchors, unknown-state propagation, duplicate identity checks and self-reported reviewer warnings are valuable; human scientific judgments remain external.
- **Measure practical reuse:** independently successful install/import or accepted task completion and repeat use matter more than stars, release announcements, LOC, or number of AI-generated PRs.
- **Green-coding claim discipline:** count review effort, failed attempts, integration, maintenance, build/runtime compute and upstream burden; only report physical energy or CO2e when measured or transparently bounded.

### Quantitative limits and practical maintainer lessons

- **Observed process change:** five overlapping active PRs retired, while unique relevant calculations, test cases, source metadata and methodological cautions were carried into their canonical branches. This is not a validated estimate of developer time, electricity, API token use, saved CO2e or downstream adoption.
- **Preflight for parallel coding agents:** compare `changed_files`, target issue, source/event IDs, command names and scientific schema with current open PRs **before** assigning an agent new work. Reserve a single canonical path per capability/source case; handle collisions by migration, not last-writer-wins.
- **Merge/release separation:** a PR that passes Python unit tests may enter technical review without authenticating human label independence, study sampling, source truth, or resource savings. Only recorded external methods/source checks can unlock scientific acceptance.
- **Reusable development outcome to measure:** compare time/effort for one consolidated tested module versus two parallel implementations including reconciliation and review; use an identical accepted functional task and report failures. Never convert PR-closure counts or code lines into kWh estimates.
