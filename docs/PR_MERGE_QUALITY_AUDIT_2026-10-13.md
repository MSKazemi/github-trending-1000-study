## Strict merge checklist (enterprise practice, distinct from scientific acceptance)

1. **Identity and scope:** current PR head SHA pinned, correct issue and base branch, no draft/unresolved review or requested changes, no overlapping branch loss; if overlap exists, document canonical merge before changing branches.
2. **Code and tests:** read whole change, architecture/API and dependency/security review, review negative/unknown/error cases, deterministic reproducibility, privacy, write-once raw data/provenance, Python version support, failure/rollback and migration compatibility.
3. **CI gate:** GitHub Actions **test (3.10)** and **test (3.12)** passed on exact current head; inspect job steps, not just combined status (GitHub legacy commit-status array may be empty); failed, queued, skipped, stale or missing checks block merge. Never assert CI passing because the PR body says so.
4. **Research/source gate:** distinguish synthetic validators from real observations; verify primary URLs/publication vs event dates, independent contradictory evidence and source rights. Preserve missingness and retain unverified hypotheses. **Do not impersonate an independent human source/methods reviewer.**
5. **Merge and follow-up:** verify GitHub `mergeable`, record the expected head SHA, merge only after checks, verify merge result and that docs/tests/data survived. Leave original science issue open where real acceptance remains incomplete.

**Repository settings recommendation (requires a maintainer to configure, not performed here):** protect `main` with no-force-push, mandatory PRs, at least one genuinely independent approval for methodological/data claims, required exact-head Python 3.10/3.12 checks and no bypass; use CODEOWNERS/rulesets if practical. Add dependency/license static/security lint and validation CI after evaluating false positives and maintenance cost. **This file does not turn such settings on.**

## Practical takeaways for the maintainer's repositories

- Separate **successful CI** from **proven usefulness and adoption**; reliable code is a prerequisite, not a field result.
- Make **one canonical tool/module per construct**, with tested migration paths; preserve competing PRs as referenced research history rather than merging redundant frameworks.
- Fail closed when source identity, license, date, artifact hash or task acceptability is unknown; do not auto-promote a hypothesis or install an agent-selected package.
- Keep README quickstarts and acceptance tasks versioned; independently verify a new user's working install/integration before claiming adoption.
- Account for actual human review, CI, maintenance, upstream burden, model calls and metered/declared-scope energy; stars and token counts do **not** measure lower CO2e.
